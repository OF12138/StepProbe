# /evaluate —— 过程评估

## 用途

对一条推理链给出结论：**是否成立 → 首错在第几步 → 属于什么错误类型**。

## 可用的 MCP 工具（stepprobe）

| 工具 | 作用 |
|---|---|
| `check_step_symbolic(steps)` | 逐步确定性校验，返回 FALSE / UNKNOWN / TRUE |
| `check_answer(pred, gold)` | 最终答案三级校验 |
| `check_format(answer, requirements)` | 形式要求校验（仅题目明确要求时用） |
| `verdict_record(run_id, verdict)` | 落盘一条评判结果 |

---

## 执行顺序（严格遵守）

### 第 1 步：确定性校验（调工具，不要自己算）

```
check_step_symbolic(steps=[...])
```

返回里有两个关键字段：

- `first_false_step` —— 确定算错的步号（1-based）。非空即判 **E3 计算错误**
- `needs_llm_review` —— 需要你做语义审查的步号列表

**只审查 `needs_llm_review` 里的步骤。** 工具已判定的步骤不要用自己的计算去覆盖 ——
算术判定交给 SymPy，你负责语义判断。这是本评估器可靠性的基础。

**关于 `check_answer`**：只有在**题目自带标准答案**（样本的 `gold_answer` 非空）时才调用。
ProcessBench 不提供标准答案，此时 —— **不要自己去判断最终答案对不对**，把 `answer_correct`
留空即可。

这不是偷懒。你一旦开始盘算「这答案看着像是对的」，后面每一步的审查都会被这个印象带偏：
答案对就倾向于放过，答案错就倾向于挑刺。**过程是否成立，与答案是否正确，是两个独立的
问题** —— 本项目的全部立论正建立在这一区分上。

> 工具返回 `TRUE` **不代表整条链成立**。每步算对不等于论证成立 —— E9 正是这么产生的，
> 所以第 3 步必须执行。

### 第 2 步：分步审查（你来判断）

对 `needs_llm_review` 中的每一步，在「前面所有步骤都成立」的前提下判断当前步是否成立。
负责三类：

- **E2 概念/定理误用** —— 必须指出定理名称与不满足的前提
- **E5 跳步推导** —— 必须写出缺失的中间环节是什么
- **E7 幻觉引用** —— 必须指出被引用对象既不在题干中，也非公认数学事实

#### 三条硬性约束

1. **不要参考最终答案是否正确。** 即使看出答案错了也不要因此提高挑错倾向；即使答案
   对了也不要因此放松审查。结果偏置会同时污染定位准确率与误报率两个核心指标。

2. **默认成立，举证判错。** 只有能指出具体问题时才判错，不确定时判「成立」。
   **宁可漏报，不可误报。**

3. **逐步独立判断。** 不要因为看到后面的步骤而反推前面步骤的对错 —— 要定位的是
   **首个**错误。

4. **只判实质错误。** 判错的对象必须是**该步本身的计算、代数变形、定理适用条件或
   概念使用不成立**。以下三类**不算过程错误**，不要判错：

   | 不算错 | 例 |
   |---|---|
   | **未证唯一性 / 论证不完整** | 题目要求 determine *all*，解答只验证了一个解，每步却都对 |
   | **表述含混** | 措辞误导（「绳子还要加上下垂量」），但随后的计算与结论均正确 |
   | **冗余步骤** | 绕远路，但每一步都成立 |

   这不是宽松，而是**口径**：本项目只覆盖步骤内的实质错误（理由见 `docs/method.md` §5
   判定范围）。判错的门槛是「这一步的某个论断不成立」，不是「这一步不够严谨」。

### 第 3 步：全局复核（必须执行）

**无论前面是否已找到错误，这一步都要跑。**

| 类型 | 复核方式 |
|---|---|
| **E1 题意误读** | 比对解答实际求解的目标与题干所问 |
| **E4 条件遗漏** | 列出题干全部条件，逐一检查是否被使用；对未使用的条件追问「去掉它结论是否改变」 |
| **E6 循环论证** | 检查是否有某步的依据实质上是待证结论 |
| **E9 答案对但过程不成立** | **无条件执行**，见下 |

#### E9 复核：不看答案对错，只看答案是否被推出来

**不要用 `check_answer` 的结果作为 E9 检查的触发条件。** 两个原因：

1. 本项目的主力数据集（ProcessBench）**不提供标准答案**，`check_answer` 根本无从调用。
   把它当触发条件，等于让 E9 检查在 447 条样本上全部静默跳过。
2. 更根本的是：**知道答案对不对，本身就是污染源。** 判断「结论是否被前序步骤真正推出」
   完全不需要知道结论对不对 —— 这是一个纯粹关于**链条内部**的问题。

所以 E9 复核对每一条链都执行，判据只有一条：

> **最终结论是否由前序步骤逻辑地推出？**

三重信号，**至少两项命中**才判定：

1. **依据充分性** —— 结论是从前面的步骤推出来的，还是在某一步突然出现的？
2. **扰动检验** —— 若题目条件轻微改变，这条链会给出什么答案？链条成立则答案应随之
   改变；实为猜测或巧合则往往不变，或变得明显荒谬。
3. **步骤删除检验** —— 删去某关键步骤后结论是否仍「成立」？若是，说明该步骤本就
   未被真正使用。

E9 误判代价很高（把正确解答判为「蒙对」会严重损害可信度），证据阈值高于其他类型。

#### 实跑教训：E9 漏掉的 5 条，错误全在「文字论断」里

修正后 E9 召回 0.643，5 条漏报**无一例外**是同一个模式：**错误藏在文字表述的论断中，
而不在任何一个可被 SymPy 检查的等式里**。L1 看不见它，L2 顺着读过去也不觉得刺眼：

| 样本 | 漏掉的论断 | 实际情况 |
|---|---|---|
| `math-568` | 「总的可能分配数 = 3」 | 样本空间界定错，应为 C(6,3)=20 |
| `math-626` | 用「竖直距离 \|d−c\|」作边长依据 | 距离概念错，恰好凑出正确面积公式 |
| `math-721` | 由 $x^2>-7$ 推出「$x>i\sqrt7$」 | 实数不等式引入虚数界；该式对一切实数恒真 |
| `olympiadbench-749` | 「$5x+9=3/2$，小于 1，故排除」 | $1.5>1$，理由本身是事实错误 |
| `omnimath-714` | 枚举「直接对应/反射/旋转」三类 | 枚举不完备，且不能证明上界 |

**据此增加一条硬性要求**：审查每一步时，把该步文字中的**每一个可判定断言**单独拎出来
核对，不要只看有没有等号。重点是这五类 ——

- **样本空间 / 分母的界定**（「总数是 N」「一共有 M 种情况」）
- **计数、周期、上界的断言**（「共 41 个」「每 9 项一循环」「最多 4 个」）
- **大小比较**（「小于 1」「大于零」）—— 这类最容易一眼扫过去
- **枚举的完备性**（「只有这三种情况」—— 凭什么只有三种？）
- **定义域 / 取值范围**（实数还是复数？开区间还是闭区间？整数约束是否被丢掉？）

对每一个这样的断言，问：**它是被证明的，还是被声称的？** 若是声称，它对不对？

> 注意这五条里没有一条需要知道最终答案。它们是链条内部的自洽性检查。

### 第 4 步：落盘

```
verdict_record(run_id="<本批次的 run_id>", verdict={...})
```

## 输出规范

`verdict` 必须是如下结构。**判错时 `evidence` 为空会被工具直接拒绝。**

```json
{
  "sample_id": "processbench-math-math-123",
  "answer_correct": null,
  "process_valid": false,
  "first_error_step": 4,
  "error_type": "E9",
  "evidence": "第 4 步由 f 连续直接得出 f 有最大值，未说明定义域为闭区间；最终答案正确系因所给区间恰为闭区间，属巧合。",
  "layer": "L3",
  "e9_signals": ["grounding", "step_deletion"]
}
```

- `answer_correct` 仅在样本带 `gold_answer` 且已调 `check_answer` 时填写，否则填 `null`
- `process_valid` 为 `true` 时，`first_error_step` 与 `error_type` 填 `null`
- `evidence` **不得为空**，且必须指向具体论断 —— 不接受「推理不够严谨」这类表述
- `layer` 记录由哪一层做出判定（L1 / L2 / L3），用于分析各层贡献
- `first_error_step` 是 **1-based**

## 批量处理

受吞吐限制，一次处理一批样本时：**整条链一次评审完再落盘**，不要逐步骤各调一次模型。
`check_step_symbolic` 一次传入全部步骤，只对它标出的 `needs_llm_review` 做语义判断。
