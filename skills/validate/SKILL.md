# /validate —— 评估器有效性验证

## 用途

**在用评估器去评测 Hy3 之前，先证明这个评估器本身是可靠的。**

做法：在 ProcessBench 等带专家人工标注的数据上跑评估器，把它的判断与人工标注对比。指标是对着**第三方标注**算出来的，不是对着自己的标注 —— 这是本项目验证结论可信的关键。

## 参数

| 参数 | 说明 | 默认 |
|---|---|---|
| `--split` | `processbench` / `prmbench` / `deltabench` | `processbench` |
| `--n` | 抽样总量 | `400` |
| `--repeats` | 稳定性验证的重复次数 | `5` |

## 流程

### 1. 取分层抽样集

调用 `dataset.next_batch(split, stratified=true, per_cell=50)`。

四个难度层 × {过程有误 / 过程无误} = 8 个子层，每层 50 条，共 400 条。

**两类各半而非按原始比例** —— 定位准确率只能在"有误"样本上算，误报率只能在"无误"样本上算，各取 50 条保证两个核心指标样本量相当。

### 2. 逐条评估

对每条样本执行 `/evaluate` 的完整流程。

**关键：此时绝对不能看标注。** `dataset.next_batch()` 返回的数据中已剥离 `label` 字段。若你在上下文里以任何方式获知了 ground truth，本次验证作废 —— 请重新开始。

### 3. 稳定性验证

从抽样集中随机取 30 条，各重复评估 5 次，统计：

- 首错步号的**众数占比**
- 错误类型的**一致率**

### 4. 计算指标

调用 `metrics.compute(run_id)`，产出：

**定位准确率**（在标注为"过程有误"的样本上）

| 指标 | 定义 |
|---|---|
| `Detection Rate` | 判定"过程存在问题"的占比 |
| `Exact Localization Acc` | 预测步号 == 标注步号 |
| `Tolerant Localization Acc (±1)` | 允许 ±1 步偏差 |

分母统一为**全部有误样本**，未检出记为定位失败。

**误报率**（在标注为"过程无误"的样本上）

`FPR = 被判为有问题的样本数 / 全部无误样本数`

**错误类型一致性** —— 映射到 PRMBench 维度后计算 Accuracy / Macro-F1 / 混淆矩阵。

所有比例指标附 Wilson 95% 置信区间。

### 5. 人工抽检（不可跳过）

从误报样本中抽取 **≥50 条**，逐条人工复核，分两类：

- **真实问题** —— 原标注漏标，评估器其实是对的
- **真误报** —— 评估器确实判错

调用 `report.export(run_id, kind="human_audit")` 生成待检清单，人工填写后存入 `results/human_audit/`。

报告同时给出**原始误报率**与**人工修正后误报率**。

> 这一步是任务书明确要求的产出（人工抽检记录），不能用自动方法替代。

### 6. 导出

`report.export(run_id)` → `results/validation/`

## 通过标准

验证结果需达到以下水平，评估器才可用于正式评测：

| 指标 | 门槛 | 理由 |
|---|---|---|
| `Detection Rate` | 显著高于随机基线 | 否则评估器没有区分力 |
| `Tolerant Localization Acc` | ≥ 0.5 | 至少一半样本能定位到出错位置附近 |
| `False Positive Rate`（人工修正后） | ≤ 0.2 | 误报会直接摧毁工具实用价值 |
| 稳定性众数占比 | ≥ 0.6 | 否则结论只是随机波动 |

**未达标时不要调参数硬凑指标。** 如实记录未达标项，分析原因（是提示词问题、切分粒度问题，还是任务本身太难），写入 `docs/report.md`。**一份诚实的失败分析比一个凑出来的漂亮数字更有价值** —— 后者在评审时经不起追问。
