# 评估方法设计说明

本文说明 StepProbe 过程评估器的完整设计与选择依据。

---

## 1. 总体思路

过程评估要回答四个问题：

1. 这条推理链**成立吗**？
2. 若不成立，**第一个错在哪一步**？
3. 这个错**属于什么类型**？
4. 若最终答案对了，**过程真的支撑得住这个结论吗**？

一个朴素方案是把整条链丢给大模型问"对不对"。这个方案有三个致命问题：

- **评估器自己会算错。** 判断 `2x+3=7 ⟹ x=2` 需要的是计算，不是判断力。让 LLM 做算术校验，等于用一个会犯错的工具去检查另一个会犯错的工具。
- **不可复现。** 同一条链两次评估结论可能不同，而任务要求给出可复现的定量指标。
- **成本高。** 逐步骤调用模型，样本量一大就跑不动 —— 在无批量 API 的 WorkBuddy 上尤其致命。

因此 StepProbe 采用**确定性层 + 推理层的级联结构**：能算清楚的绝不交给模型判断，交给模型的都是真正需要语义理解的部分。

---

## 2. 级联流水线

```
输入：题目 problem、解答文本 solution、标准答案 gold

  L0  步骤切分            ──▶  steps[]           （MCP 工具，规则）
       │
  L1  确定性校验          ──▶  逐步 verdict      （MCP 工具，SymPy）
       │    · 最终答案校验
       │    · 步骤等式校验
       │    ├── 命中错误 ──▶ 直接判定 E3 / E8，记录步号，流程结束
       │    └── 未命中   ──▶ 继续
  L2  分步审查            ──▶  逐步 verdict      （Hy3）
       │    · 仅对 L1 无法判定的步骤
       │    ├── 命中错误 ──▶ 判定 E2 / E5 / E7，记录步号
       │    └── 未命中   ──▶ 继续
  L3  全局复核            ──▶  链级 verdict      （Hy3）
            · E1 / E4 / E6 / E9

输出：{process_valid, first_error_step, error_type, evidence, layer}
```

**为什么是"短路"而非"全跑"**：任务只要求定位**首个**错误步骤。一旦 L1 在第 k 步发现计算错误，第 k 步之后的推导都建立在错误结论上，继续评审没有意义。短路能省下大量模型轮次。

**唯一的例外是 L3。** 即使前面全部通过，L3 仍必须执行 —— 因为「答案正确但过程不成立」（E9）恰恰发生在所有单步都"看起来没错"的情况下。

---

## 3. L0 步骤切分

**目标**：把自由文本解答规整为可索引的原子步骤，使"第 k 步出错"这个说法有确切含义。

**做法**：优先要求 Solver 直接输出结构化 JSON（见 `skills/solve/`），避免事后切分。对公开数据集中已有的解答文本，按以下优先级切分：

1. 数据集自带的步骤分隔标记（ProcessBench / PRMBench 已按步骤组织，直接沿用其索引）
2. 显式编号（`Step 1`、`①`、`(1)`）
3. 段落与换行
4. 句末标点 + 公式块边界

**关键约束：切分粒度必须与标注对齐。** 若我们把标注中的一步拆成两步，步号就整体错位，定位准确率会被系统性低估。因此：

- 对 ProcessBench / PRMBench / DeltaBench，**一律使用数据集原有的步骤索引，不重新切分**
- 仅对自建中文子集与 Hy3 新生成的解答使用上述规则
- 指标同时报告 `Exact` 与 `±1 容忍` 两个版本，前者衡量严格对齐，后者吸收粒度差异

## 4. L1 确定性校验（MCP 工具，零 LLM）

### 4.1 最终答案三级校验 `check.answer()`

| 级别 | 方法 | 处理的情况 |
|---|---|---|
| 1 | 表达式规范化后字符串比对 | `1/2` vs `0.5` vs `\frac{1}{2}` |
| 2 | SymPy 符号等价 `simplify(a - b) == 0` | `(x+1)^2` vs `x^2+2x+1` |
| 3 | 随机数值代入，多点比对 + 容差 | 符号化简超时或失败时的兜底 |

三级依次尝试，任一级判定相等即通过。设计依据：LaTeX 答案形式高度自由，单纯字符串比对会产生大量假阴性，而纯符号化简在复杂表达式上可能超时。

### 4.2 步骤等式校验 `check.step_symbolic()`

从步骤文本中抽取形如 `LHS = RHS` 的等式，用 SymPy 判定是否成立。

**这一层只做"能确定判假"的判定，不做"确定判真"。** 三种返回值：

- `FALSE` —— 等式经符号 / 数值校验确定不成立 → 判定 **E3 计算错误**，短路
- `UNKNOWN` —— 无法解析（含自然语言推理、几何论述、无等式）→ 交给 L2
- `TRUE` —— 等式成立 → **仍需交给 L3**，因为"每步算得对"不等于"整体论证成立"

**为什么不用 `TRUE` 直接放行**：这正是 E9 的来源。一条链可以每一步的算术都正确，却建立在误读题意或误用定理之上。

### 4.3 格式校验

按题目要求（区间形式、最简分数、保留位数、单位）做规则校验 → **E8**。

## 5. L2 分步审查（Hy3）

**只对 L1 返回 `UNKNOWN` 的步骤执行。**

### 提示词设计原则

1. **给定前缀，只判当前步。** 输入 `problem` + `steps[0:i]` + `step[i]`，问"在前 i 步都成立的前提下，第 i 步是否成立"。这样定位到的必然是**首个**错误，而不是被下游连锁错误干扰。

2. **不告诉模型最终答案是否正确。** 否则会产生严重的结果偏置 —— 知道答案错了就倾向于到处挑错，知道答案对了就倾向于全部放行。这个偏置会同时污染定位准确率和误报率两个核心指标。

3. **要求给出证据，而非仅给标签。** 输出必须包含 `evidence` 字段，指明具体是哪个论断不成立。无证据的判错视为不可信，在 L3 中降权。

4. **默认成立，举证判错。** 明确要求：只有在能指出具体问题时才判错，不确定时判"成立"。这是一个刻意的保守设置 —— **宁可漏报，不可误报**，因为误报率是任务书要求的核心验证指标，且误报会直接摧毁工具的实用价值。

5. **整链单次调用返回数组。** 受吞吐约束（README §10），一次调用传入整条链，要求返回逐步骤 verdict 数组，而非每步一次调用。以提示词约束模型"逐步独立判断，不要因为后续步骤反推前面的对错"来近似前缀独立性。

### 判定范围

L2 负责 **E2 概念/定理误用**、**E5 跳步推导**、**E7 幻觉引用** —— 三者的共同点是需要数学知识与语义理解，无法由符号计算判定。

**只判实质错误**（P7 人工抽检后确定的口径，见 `docs/report.md` §5.4，已写入 `configs/taxonomy.yaml: principles.substantive_errors_only`）：

一个步骤被判错，必须是**该步本身的计算、代数变形、定理适用条件或概念使用不成立**。
以下三类**不计入过程错误**：

- **未证唯一性 / 论证不完整** —— 每步都对，但整体论证有缺口（如题目要求 determine *all*，解答只验证了一个解）
- **表述含混** —— 措辞误导但数值与结论均正确
- **冗余步骤** —— 绕远路但每步成立

理由：ProcessBench 的标注就是按此口径做的，换口径会让指标失去可比性；且「论证是否完整」
缺少客观界线，纳入后会引入大量不可复现的判断。**代价**是本项目不覆盖上述三类问题 ——
这是明确的能力边界。评估结果与标注因此类差异而不一致时，应判为 `criterion_gap` 并从
误报 / 漏报统计中剔除，而不是记在任何一方账上。

## 6. L3 全局复核（Hy3）

**无论前面是否短路，只要 L1/L2 未判错就必须执行。**

输入完整推理链 + 题目 + `check.answer()` 的结果，判定四类链级问题：

| 类型 | 复核方式 |
|---|---|
| E1 题意误读 | 比对解答实际求解的目标与题干所问 |
| E4 条件遗漏 | 列出题干全部给定条件，逐一检查是否被使用；对未使用的条件追问"去掉它结论是否改变" |
| E6 循环论证 | 检查是否存在某步的依据实质上是待证结论 |
| **E9 答案对但过程不成立** | **仅在 `check.answer()` 判定答案正确时触发**：追问"这条链是否真的推出了这个答案，还是答案来自猜测、数值巧合、或错误互相抵消" |

### E9 的交叉验证

E9 是本项目最难也最有价值的判定。单靠一次提问不可靠，因此采用三重信号：

1. **依据充分性** —— 最终答案是否由前序步骤逻辑推出，而非凭空出现
2. **扰动检验** —— 若题目条件轻微改变，这条推理链会给出什么答案？若链条正确，答案应随之改变；若链条实为猜测，往往给出与原来相同或明显荒谬的结果
3. **步骤删除检验** —— 删去某个关键步骤后结论是否仍"成立"。若是，说明该步骤本就未被真正使用，链条存在虚假依赖

三个信号中至少两个指向问题，才判定 E9。设计依据：E9 的误判代价很高（把正确解答判为"蒙对"会严重损害可信度），因此要求更强的证据阈值。

## 7. 指标定义

### 7.1 定位准确率（在标注为"过程有误"的样本上）

| 指标 | 定义 |
|---|---|
| `Detection Rate` | 评估器判定"过程存在问题"的样本占比 |
| `Exact Localization Acc` | 预测首错步号 == 标注步号 的占比 |
| `Tolerant Localization Acc (±1)` | 允许 ±1 步偏差 |

分母口径统一为**全部有误样本**（未检出记为定位失败），避免只在"检出的样本"上算准确率而虚高。

### 7.2 误报率（在标注为"过程无误"的样本上）

`False Positive Rate = 被判为有问题的样本数 / 全部无误样本数`

**人工抽检**：覆盖三类分歧（误报 / 漏报 / 定位偏差），逐条复核并分为四类：

| 结论 | 含义 | 对指标的处理 |
|---|---|---|
| `evaluator_wrong` | 评估器错，原标注正确 | 不动，计为评估器失误 |
| `evaluator_right` | 评估器对，原标注有问题 | **改写标注**后重算 |
| `criterion_gap` | 双方都没错，判定准则不同（§5 判定范围） | **从统计中剔除** |
| `needs_human` | 预审无法定论 | 必须人工独立判断 |

> 抽检表最初只收「误报」一类。实跑中误报率为 0/8，清单为空，人工抽检无从下手 ——
> 而漏报与定位偏差同样需要确认「究竟是评估器错了，还是原标注有问题」。已扩为三类。

**流程分两步，且严格分离**：

1. `scripts/pre_audit.py` 生成**判断包**（题干、全部步骤并标出双方首错位置、L1 独立符号
   校验、评估器证据），附 Claude 的**预审意见**与置信度。目的是把人工的工作从「从头读题
   分析」降为「逐条确认」。
2. `scripts/apply_audit.py` 读取人工填写的 `human_verdict`，按 `scripts/audit_corrections.json`
   应用标注修正并重算指标。**该脚本会校验每条修正在抽检表中都有对应的人工结论，否则拒绝
   执行** —— 防止预审意见被当成人工结论用上。

**报告必须同时给出两套指标**：以原标注为准的（可与该数据集上的其他工作对照）与人工修正
后的（评估器的真实表现），并分别写明「人工确认了 N 条、推翻了 M 条」。预审不冒充抽检。

### 7.3 错误类型一致性

将 E1–E9 映射到 PRMBench 标注维度后计算 Accuracy / Macro-F1 / 混淆矩阵。混淆矩阵比单一准确率更有信息量 —— 它能显示哪两类错误容易被混淆（预期 E5 跳步 与 E7 幻觉引用 之间、E2 定理误用 与 E4 条件遗漏 之间存在混淆）。

### 7.4 稳定性

同一条链**独立重新评估**（清空上下文重走完整流程，看不到上一趟任何判断），统计：

- 首错步号的**众数占比**
- 错误类型的**一致率**

**必须是独立重评，不能是重复落盘同一结果。** 首轮曾把同一条 verdict 原样重提 5 次，得到
众数占比 1.0 —— 那个 1.0 只证明了「同一份 JSON 存五遍还是它自己」，却长得跟满分一样。
`metrics.stability()` 现在比对完整内容指纹（步号 + 类型 + 证据），逐字相同即判机械重复，
`valid` 置 false 并把指标置空：**宁可没有指标，不要假满分。**

## 8. 结果分析口径

### 答案 × 过程 交叉表

|  | 过程正确 | 过程有误 |
|---|---|---|
| **答案正确** | 真正掌握 | **E9：蒙对 / 巧合** ← 核心关注 |
| **答案错误** | 罕见（应人工核查是否为标注问题） | 常规错误 |

单看 pass@1 只能看到第一列与第二列的合计。本项目的核心贡献就是把右上角这一格拆出来。

### 难度分层分析

按 T1–T4 分别报告答案准确率与过程正确率，识别**两条曲线开始分离的难度区间** —— 那里就是模型"开始靠感觉而非靠推导"的临界点。

### Max Mode 消融

WorkBuddy 提供 Max Mode 开关（唯一可控的模型侧变量）。在开 / 关两种配置下跑同一批题目，比较：

- 最终答案准确率的变化
- **过程正确率的变化**
- **E9 占比的变化**

关键问题：Max Mode 带来的提升，是让推导更严谨（过程正确率同步上升、E9 占比下降），还是只是让答案更容易蒙对（答案准确率上升但 E9 占比不降反升）？

## 9. 已知局限

诚实记录，写入最终分析报告：

1. **评估器以 Hy3 评判 Hy3**，存在同源偏置 —— 模型可能对自己犯的错更不敏感。有效性验证使用的是**其他模型生成**的推理链（ProcessBench 中的解答来自多个模型），一定程度上缓解但未消除该问题。
2. **步骤切分粒度**与人工标注可能不完全对齐，故同时报告 `±1` 容忍指标。
3. **样本量受吞吐限制**，结论基于约 400 条分层抽样，报告中标注置信区间。
4. **E9 的标注稀缺** —— 公开数据集中"答案对但过程错"的标注样本本就不多，该项指标的置信度低于其他项。
