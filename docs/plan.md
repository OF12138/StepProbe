**L1 在 447 条真实样本（3172 步）上的实测结果**

| 指标 | 数值 |
|---|---|
| 触发率 | 27 / 447 = 6.0% |
| 触发时精确命中 | 11 / 27 = 40.7% |
| 触发时 ±1 命中 | 16 / 27 = 59.3% |
| **触发时误报率** | **1 / 27 = 3.7%**（95% CI 0.7%–18.3%） |

步骤级：FALSE 1.17% / TRUE 11.29% / UNKNOWN 87.55%。

87.5% 的步骤 L1 判不了 —— 这符合预期且正是设计意图：L1 只负责能被符号计算
确定判定的部分，剩下的交给 L2/L3。它的价值不在覆盖率，而在**触发时几乎不会错**。

**唯一剩下的那条「误报」很可能不是误报**：`11.5098 × 720 = 8286.656`，
正确值为 8287.056。这是解答里的真实算错，而 ProcessBench 把该样本标注为
过程无误 —— 属于标注漏标。已列入 P7 人工抽检的「真实问题」候选。

### P2 的关键教训：确定性层也会看走眼

初版 L1 的实测误报率是 **33.3%**（12/36），远超 ≤20% 的门槛，直接动摇了
「把能确定判定的事从 LLM 手里拿走」这个立论。

逐条查看 12 条误报后发现：**没有一条是真正的判断分歧，全部是解析失败。**
根因是规范化器过于宽容 —— 遇到不认识的 LaTeX 命令就剥掉继续解析，结果
解析出垃圾却「成功」了：

| 原文 | 剥掉后 | 判定 | 实际 |
|---|---|---|---|
| `\varphi(41) = 41 - 1` | `(41) = 40` | FALSE | φ(41)=40 ✓ |
| `\binom{40}{17} = \binom{40}{23}` | `(40)(17) = (40)(23)` | FALSE | 组合数相等 ✓ |
| `f(2) = 8 + 6 = 14 \tag{7}` | `14 * 7` | FALSE | ✓ |
| `\[71+72=143\] \[143+73=216\]` | 跨块拼成假等式 | FALSE | ✓ |

修复分四步，每一步都由实测数据驱动：

1. **命令白名单**（33.3% → 12.5%）—— 从「不认识就剥掉」改为「不认识就返回
   None」，与文档里早就写下的「解析不了就返回 None，绝不猜」一致。这条原则
   本来就在，只是初版实现没有贯彻。
2. **公式块先切分** —— `\[ \]` `$$` 内的等式互相独立，必须先切开
3. **带余除法与函数下标豁免**（12.5% → 6.7%）—— `3970 ÷ 8 = 496 remainder 2`
   的右侧是「商 + 余数」，不是一个数值
4. **整除取整惯用法豁免**（6.7% → 3.6%）—— `49 ÷ 9 = 5` 指分成 5 组余 4；
   但豁免只在商恰好等于向下取整时生效，`49 ÷ 9 = 6` 仍会被判错

10 条误报已全部固化为回归测试用例。

5. **进制标注豁免**（P6 之后补）—— `212_{10}` 里的下标是**进制**不是下标。
   这一条不是初版遗留，而是 P6 引入的**回归**：为了让 `\log_{10}(2)` 与
   `log_10(2)` 判等，规范化器加了 `_{X}` → `_X`，进制标注随之从「解析失败落到
   UNKNOWN」变成「能解析并判 FALSE」。进制转换题里每一步都带标注，误报成串出现，
   全抽样集误报率一度 3.6% → **10.0%**。

> **教训：给 A 修的 bug 会从 B 那里出来。** L1 校验器与答案比对器共用
> `normalize()`，而这次改动的动机完全来自答案比对那一侧，改的时候根本没想到
> L1。发现它靠的是「改完共享代码后把所有依赖它的实测数字重跑一遍」——
> 单测全绿，是重测 §4.1 才暴露出来的。

**这段经历本身要写进分析报告**：它说明「用确定性方法替代 LLM 判断」不是免费
的可靠性 —— 确定性方法同样会因为实现缺陷而系统性出错，而且因为它看起来
「确定」，这类错误反而更不容易被怀疑。

| 工具 | 作用 |
|---|---|

- **工具逻辑与 MCP 协议解耦** —— 逻辑在 `tools.py`，`__main__.py` 只做注册。

  ground truth 只在 `metrics_compute` 阶段从样本集读取。有专门测试断言批次
  JSON 里不出现任何标注字段。
- **判错必须举证** —— `verdict_record` 走 pydantic 校验，`process_valid=false`
  却没填 `evidence` 会当场被拒，而不是等写报告时才发现证据是空的。
- **兼容 mcp 1.x 与 2.x** —— 2.x 把 `FastMCP` 改名为 `MCPServer`，两个都试。
  WorkBuddy 用户机器上版本可能不一，免得因 SDK 版本对不上白折腾。

#### 问题一：ground truth 泄漏（严重，我的 bug）

loader 把 ProcessBench 的原始 `raw_label`（0-based 首错步号）塞进了
`meta`，而 `without_label()` 只清 `label` 不清 `meta` —— **标注就这么随批次
发了出去**。

更糟的是测试没抓到：`test_mcp_tools.py` 的夹具 `meta` 是空的，
**测试全绿而真实数据在泄漏**。是 WorkBuddy 那边的 agent 主动声明「返回了
`meta.raw_label`，我全程忽略」才保住了这轮盲评。

修复：
- `SAFE_META_KEYS` **白名单** —— 新增 meta 字段默认不外发，要外发必须显式加进白名单
- 新增 `tests/test_no_label_leak.py`，**用真实数据集全量校验**，不只用夹具
- 泄漏检查改为结构化断言（子串匹配会被 `"label": null` 误报）

教训：这类 bug 静默作废整轮验证 —— 不报错、不崩溃，指标照样算得出来，
只是全都不可信。**用夹具测隔离逻辑，用真实数据测契约。**

#### 问题二：稳定性指标是假的

首轮的稳定性做法是把同一条 verdict 原样重提 5 次，得到
`step_mode_ratio = 1.0`。这个 1.0 只证明了「同一份 JSON 存五遍还是它自己」，
与评估器稳定性毫无关系，却长得跟满分一样。

修复：`stability()` 比对每次评判的完整内容（步号 + 类型 + 证据），逐字相同
即判定机械重复，`valid=false` 且指标置空 —— **宁可没有指标，不要假满分**。

真实稳定性验证必须是清空上下文的独立重评。

#### 问题三：抽检表只收误报，太窄

误报率 0/8 时抽检表为空，人工抽检无从下手。WorkBuddy 把这误诊为
「服务端未持久化样本内容」并自行写脚本重建了一份 —— 实际 0 行是**正确行为**。

但设计上确实有缺口。修复：抽检表改为覆盖三类分歧，并加 `disagreement_kind` 列：

| 类型 | 含义 |
|---|---|
| `false_positive` | 标注无误、评估器判错（任务书要求抽检的核心类别） |
| `missed` | 标注有误、评估器漏过 |
| `mislocalized` | 都判有误但步号不同 |

漏报与定位偏差同样需要人工确认「是评估器错了，还是原标注有问题」，
而且这两类反而更常出现。同时对同一样本去重，避免稳定性重复评估把清单撑成 N 倍。

#### 一个正面发现：L1 确实赚到了

`check_step_symbolic` 在 omnimath-7 第 1 步抓到 `1+2+…+666 = 1998`
（正确值 1563）—— WorkBuddy 的 agent 起初把这条判为「过程无误」，
看到 L1 的 FALSE 后改判为 E9。

这正是「把能确定判定的事从 LLM 手里拿走」的价值：**模型会放过的算术错误，
SymPy 不会**。

### P6 评测执行 + Max Mode 消融（✅ 已完成，结论为 null）

**要回答的问题**：Max Mode 是让推导更严谨，还是只是让答案更容易蒙对？这两件事在
「答案正确率」这一个数字上长得一模一样，必须同时测答案正确率与过程成立率才分得开。

**实施时发现的拦路问题：ProcessBench 没有标准答案。** 4 个 parquet 的列只有
id / generator / problem / steps / final_answer_correct / label，447 条样本的
`gold_answer` 全为空。没有标准答案，Hy3 自己解出来的答案就无从判分，P6 无法进行。

**解法**：从数据集里反推。被标为 `final_answer_correct=True` 的解答，其最终答案
按数据集的断言就是对的 —— 抽出其中的 `\boxed{...}` 即可。可靠性不靠假设：
ProcessBench 里有 110 道题被两个以上模型答对过，构成天然的**交叉印证集**，
两次独立抽取的一致率就是抽取器的实测可靠性。

| | 实测 |
|---|---|
| boxed 抽取率 | 90.1%（1532/1700） |
| 交叉印证一致率 | **95.5%**（105/110） |
| 产出题目集 | 160 道，四层各 40 |

**交叉印证顺带验出了一个 bug。** 第一版一致率只有 79.1%，逐条看下去发现 23 处
不一致里有 20 处根本不是答案不同，而是 `check_answer` 对装饰差异过严：
`x = √2` vs `√2`、`4^\circ` vs `4`、`17.5\%` vs `17.5`、`1 and 3` vs `1, 3`。
这个 bug 若不修，P6 里 Hy3 的答案会因为写法不同被大量误判为答错，
答案正确率被系统性低估 —— 而 P6 恰恰要靠它。修完 79.1% → 95.5%。

> 值得记一笔：**这个 bug 是被一个「顺手做的一致性检查」逼出来的，不是被单测。**
> 单测里的答案都是我写的，写的时候就按同一种风格写；只有真实数据里两个模型
> 各写各的，才会把这种差异暴露出来。

**统计设计**：同题配对。两个 arm 解同一批题，比的是配对差分 —— 题目难度、
标准答案抽取误差这些成对出现的偏置在差分中抵消。因此 `--min-agree` 默认取 1
（若只要有交叉印证的题，T2 与 T4 一道都剩不下，会得到一个只有 T3 的畸形集合）。
判别信号是**答对的题里过程不成立的比例**：它上升就说明 Max Mode 只是蒙得更准。

**人工环节**：在 WorkBuddy 中执行 `/ablate` —— Max Mode 关一轮、开一轮解同一批题，
再逐条评估，最后 `python scripts/p6_score.py --run <run_id>`。

#### 三条实施教训

**一、口径要和实验目标对齐，这件事必须在设计阶段查。** §5.4 定下「只判实质错误」
的口径是为了 P5 的可判定性，完全正确；但 P6 想测的「Max Mode 是否让推导更严谨」，
其主要表现恰恰是铺开程度（步数均值 4.10 vs 3.38），而这正是该口径明确不判的一维。
两个决定各自都对，凑在一起就是结构性错配。**代价是 320 条解答加 320 条评估。**

**二、「零判错」这类数字必须自证。** 过程成立率 1.000 出来时，第一反应应该是
怀疑评估器而不是庆祝。用的自证手段是一个内部一致性检验：**答案错的题，过程里
必然有错**。命中 9 道，逐条查出 1 条真漏报（`p6-t3-034`，三个平方根做成两个）、
1 条 gold 本身错、2 条归一化漏网、4 条数据集缺陷。这个手段不依赖外部标注，
成本极低，应该成为任何「过程成立率」数字的标配。

**三、真实数据里的风格差异是单测的盲区（第二次踩到）。** 160 道题只产生 10 条
配对差异，其中 7 条是写法不同而非答案不同 —— 而且方向系统性偏斜，因为两臂
恰好一个写 ASCII、一个写 LaTeX。查出六个归一化 bug（千位分隔符吃元组逗号、
`\b` 在下标前失效、按首尾字符判括号包裹、集合构造式被自信判错、裸单位词、
`±` 记号）。修复后答案正确率 0.936 → 0.981，配对差分反而更干净
（净 −2/p=0.688 → 净 −3/p=0.250）。

> 这和 `check_answer` 那次是同一个教训的第二次出现：单测里的两个答案都是自己
> 写的，写的时候按同一种风格写。**只有让两个独立来源各写各的，风格差异才会
> 暴露出来。** 第一次是交叉印证，这次是两臂对比 —— 都是「顺手做的一致性检查」
> 比单测更早发现问题。

### P7 人工抽检 —— 如何把人工降到最低（✅ 已完成）

任务书要求「经人工抽检确认其中属于真实问题与属于误报的比例」，**这一步无法用自动方法替代**。做法是把它从「逐条判断」降为「逐条确认」：

1. `scripts/pre_audit.py` 对每条分歧生成**判断包**：题干、全部步骤（双方首错位置已标出）、L1 独立符号校验、评估器证据，附 Claude 预审意见与置信度
2. `audit_sheet.csv` 每行只需人工填一个 `human_verdict`
3. `scripts/apply_audit.py` 读回人工结论，按 `audit_corrections.json` 改写标注并重算指标

**实际结果**（run-20260903T141258Z，16 条分歧）：

| | 条数 |
|---|---|
| 人工确认预审意见 | 14 |
| 人工推翻预审意见 | 1 |
| 预审标为 `needs_human`、人工独立判断 | 1 |

**预审准确率 14/15，人工实际耗时约 1 小时**（原估 30–45 分钟，低估了 —— 其中 4 条需要独立复算、1 条需查原始 Omni-MATH 补全题干）。

### P7 的两个设计决定，事后看都值得

**① 抽检表必须覆盖三类分歧，不能只收误报。**
最初只收「误报」。实跑误报率 0/8，清单为空，人工抽检无从下手。漏报与定位偏差同样需要确认「是评估器错了，还是原标注有问题」—— 事实上 4 条「标注有问题」中有 3 条来自漏报与定位偏差，只收误报就全漏了。

**② 预审与抽检必须机制性分离，不能只靠自觉。**
`apply_audit.py` 会校验修正文件里的每一条在抽检表中都有对应的 `human_verdict`，否则拒绝执行；`tests/test_audit_pipeline.py` 进一步钉死「修正方向必须与人工结论一致」。理由是：一旦这条约束失效，报告里的数字会失去它宣称的来源，**而且从结果上完全看不出来**。这类问题不能靠写一句「诚实说明」防住。

诚实说明照写不误：报告 §5 分别写明「人工确认了 N 条、推翻了 M 条」，**不把 Claude 的复核伪装成人工抽检**。

### P8 报告与 Demo

`docs/report.md` 已完成（含 P6 结果，§6）。分镜脚本见 `docs/demo.md` —— 2 分钟，
四个镜头，每个数字都指向 `results/runs/` 里的具体文件。

**人工环节**：按分镜录屏。纪律写在分镜末尾，核心一条是**不要跳过失败** ——
演示时评估器若判错了就留在片子里并说明，这比重录十遍取一条完美的更有说服力。

## P1 实测发现（四处修正了原设计）

原设计基于论文描述与部分抽样，P1 实现时核实了全量真实数据，有四处需要修正。

### 修正一：E9 并不稀缺，且随难度急剧上升

**这是本项目目前最有价值的发现。**

先前只看了 gsm8k（400 条）就下结论说 E9（答案对但过程错）仅占 1.75%、稀缺到必须全量取用。跑完全量 3400 条后，这个判断是**错的**：

| 难度层 | 题源 | 总数 | E9 数量 | **E9 占比** |
|---|---|---|---|---|
| T1 | GSM8K | 400 | 7 | **1.75%** |
| T2 | MATH | 1000 | 94 | **9.40%** |
| T3 | OlympiadBench | 1000 | 161 | **16.10%** |
| T4 | Omni-MATH | 1000 | 259 | **25.90%** |
| **合计** | | **3400** | **521** | **15.32%** |

**从 T1 到 T4，E9 占比翻了近 15 倍。**

这个梯度本身就是一条值得写进报告的结论：**题目越难，「答案对但推理站不住」的比例越高**。换句话说，只统计最终答案准确率，在难题上会系统性高估模型能力 —— 而这正是本项目立论的实证支撑。它同时直接回答了任务书要求的「模型能力边界与临界点分析」。

相应地，抽样策略改回三类等量（`per_cell: 40`），不再对 E9 特殊照顾；`TAKE_ALL` 机制保留但置空，留给以后自建中文子集中可能真正稀缺的类别。

抽样集实际规模：**447 条**（T1/e9 仅 7 条不足 40，按规则全取）。

### 修正二：ProcessBench 不提供标准答案

原 Schema 设计里有 `gold_answer` 字段。实测发现 ProcessBench **没有**这个字段，只提供 `final_answer_correct` 布尔值。

影响：`check.answer()` 无法在 ProcessBench 上验证 —— 只能直接采用它给出的布尔值。答案校验器的正确性改由 P2 自建的等式测试集回归。`gold_answer` 在 Schema 中保留为可选字段，供 DeltaBench 与自建中文子集使用。

### 修正三：DeltaBench 只能验证定位能力

实测 DeltaBench 的 math + code 子集共 935 条，**`final_correct` 全部为 0** —— 即全是答案错误的样本。

影响：DeltaBench **无法**用于测量误报率，也不含任何 E9 样本。它的用途收窄为**定位能力的跨域泛化验证**（数学 562 + 代码 373）。误报率与 E9 相关指标只在 ProcessBench 上给出。

另：其分段数据在 `sections` 字段（dict 列表），不是 `sections_content`（那是拼接后的单个字符串）。

### 修正四：步号基准

ProcessBench 的 `label` 是 **0-based**，`-1` 表示全部步骤正确；本项目统一 **1-based**。

转换：`first_error_step = label + 1 if label >= 0 else None`

这是容易悄悄出错的地方 —— 差一位不报错，只会让定位准确率被系统性低估。已由单元测试覆盖，且 loader 中加了越界断言。

## 依赖精简

原计划依赖 `datasets` 库（体积大、装起来慢）。实测 ProcessBench 的 parquet 文件四个 split 合计仅约 3.3 MB，因此改为**直接用 urllib 下载 parquet + pandas 读取**，去掉该依赖。

保留依赖：`sympy`、`pydantic`、`pyyaml`、`pandas`、`pyarrow`、`mcp`、`tqdm`、`statsmodels`。
