## 1. 问题：答对了，不代表过程对

**画面**：`docs/report.md` §1 的 E9 占比表。

> 大模型做数学题，答对越来越容易，但「答得对不对得住」很少有人查。
>
> ProcessBench 全量三千四百条实测：答案对、过程却站不住的比例，从小学题的百分之一点七五，升到竞赛题的百分之二十五点九。题目越难，只看答案越会高估模型能力。

## 2. 方案：先把能算的算掉

**画面**：`README.md` 的架构图，停在 L1 符号校验。

> StepProbe 用四层级联，关键在第二层。
>
> 等式成不成立，SymPy 能确定性地算出来，不需要问模型。这一层在四百四十七条样本上误报率百分之三点七，且不消耗任何模型轮次。

## 3. 实跑：在 WorkBuddy 里评一条推理链

**画面**：WorkBuddy 新会话。粘贴下方的演示样本，依次展示 `check_step_symbolic` 的调用、返回中的 `needs_llm_review`，以及最终评判里的 `evidence`。

> 我给它一条真实的推理链，来自 Omni-MATH。第一步在算 1998 的真因数之和。

> 它调了 MCP 工具，没有自己心算。返回里的 `needs_llm_review`，就是模型真正要审的那几步。

> 第一步判为不成立 —— 这些真因数加起来是 1563，不是 1998。
>
> 但题解下一句「所以不是完全数」又是对的。人会顺着正确结论滑过去，SymPy 不会。
>
> 再看 evidence：写不出证据的判错，工具直接拒绝落盘。

## 4. 评估器是否可信

**画面**：`results/runs/run-20260903T141258Z/audit_summary.md` 的指标表，然后切到 `docs/report.md` §5.1 的 olympiadbench-892。

> 凭什么信它？我们拿 ProcessBench 的第三方专家标注来对。
>
> 但标注也是人做的。十六条不一致的样本，我们逐条人工定责 —— 是评估器错，还是标注错。结果四条是标注错了。
>
> 比如这道题，解答称末位每九项一循环，真实周期是十；末位之和真值 225，它算成 245，答案才对。标注漏了它。
>
> 定责之后：检出率零点八五七，误报率二十三分之零。

## 演示样本

第 3 段使用的推理链，来自 ProcessBench 的 `omnimath-7`，可以直接粘贴到 WorkBuddy 复现：

```
/evaluate

题目：A number p is perfect if the sum of its divisors, except p, is p.
f(n)=0 if n is perfect; f(n)=0 if the last digit of n is 4; f(a·b)=f(a)+f(b).
Find f(1998).

步骤 1：先判断 1998 是否为完全数。1998 的真因数为
1, 2, 3, 6, 9, 18, 27, 37, 54, 74, 111, 222, 333, 666，
其和为 1 + 2 + 3 + 6 + 9 + 18 + 27 + 37 + 54 + 74 + 111 + 222 + 333 + 666 = 1998。
由于真因数之和不等于 1998，故 1998 不是完全数。

步骤 2：检查 1998 的末位数字为 8，不等于 4，故第二条规则不适用。

步骤 3：将 1998 分解质因数：1998 = 2 × 3^3 × 37，再用可乘性展开。
```

这条推理链的第 1 步等式不成立（真因数之和为 1563），但紧接着的结论「1998 不是完全数」恰好正确。L1 会在第 1 步判定不成立，并在 `evidence` 中给出该等式。
