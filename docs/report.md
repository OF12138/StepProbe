## 1. 场景选择理由

大模型在数学推理上「答对」越来越容易，但「答得对不对得住」很少被检验。同一个正确答案，背后可能是一条严谨推导，也可能是猜选项、数值巧合、或误用定理却恰好抵消。

选择数学可验证场景，是因为它同时满足两个条件：**存在明确标准答案**（可自动校验），且**存在大量带人工步骤级标注的公开数据**（可验证评估器本身）。后者是关键 —— 没有第三方标注，「评估器是否可靠」就只能自说自话。

### 数据侧的实证支撑

P1 跑完 ProcessBench 全量 3400 条后，得到一条直接支撑本项目立论的数据：

| 难度层 | 题源 | 总数 | **「答案对但过程错」占比** |
|---|---|---|---|
| T1 | GSM8K | 400 | 1.75% |
| T2 | MATH | 1000 | 9.40% |
| T3 | OlympiadBench | 1000 | 16.10% |
| T4 | Omni-MATH | 1000 | 25.90% |
| 合计 | | 3400 | **15.32%** |

**从 T1 到 T4，该比例翻了近 15 倍。** 换句话说：**只统计最终答案准确率，在难题上会系统性高估模型能力** —— 到了 Omni-MATH 这一层，每四个「答对」里就有一个推理站不住。

这条梯度同时反向验证了难度分层的有效性：如果 T1–T4 只是题源不同而非推理难度递增，不会出现这样的单调曲线。

## 2. AI 应用的解决方案

WorkBuddy 是可执行本地任务的 Agent 工作站，支持 MCP Server 与 Skills。因此本项目不是「调用大模型 API 的脚本」，而是**挂载到 WorkBuddy 上的确定性工具 + 评估 Skill**，由其中的 Hy3 驱动整个流程。

```
WorkBuddy (Hy3)                    StepProbe MCP Server（纯 Python，零 LLM）
  Skills: /solve /evaluate /validate     8 个确定性工具
     │                                        │
     │  L0 步骤切分                            │  dataset_next_batch  取样（剥离标注）
     │  L2 分步语义审查   ←──── MCP ────→      │  check_step_symbolic 逐步等式判定
     │  L3 全局复核 / E9                       │  check_answer        答案三级校验
     │                                        │  verdict_record      落盘（判错必举证）
     └────────────────────────────────────────┤  metrics_compute     指标
                                              │  report_export       抽检清单
```

### 核心设计依据：把能确定判定的事从 LLM 手里拿走

纯 LLM-as-judge 有个根本弱点 —— **评估器自己也会算错**。`2x+3=7 ⟹ x=2` 应该由 SymPy 判定，而不是由另一个大模型「觉得」它对不对。因此：

- 能被符号计算判定的 → MCP 工具（计算错误、答案校验、格式校验）：确定、免费、可复现
- 需要语义理解的 → Hy3（定理前提、是否跳步、是否循环论证）：LLM 不可替代
- 先跑确定性层，再跑推理层：大量计算类错误在 L1 即被拦下，减少昂贵的模型轮次

这一切分同时缓解了 WorkBuddy 无批量 API 的吞吐约束。

## 3. 评估维度设计依据

九类错误体系（E1–E9，完整判定标准见 `configs/taxonomy.yaml`），每类都配可操作判定依据与正反例，刻意避免「较好地满足要求」这类无从复核的表述。

两条贯穿全局的原则：

**默认成立，举证判错。** 只有能指出具体问题时才判错。这是刻意的保守设置 —— 误报率是任务书要求的核心指标，且误报会直接摧毁工具的实用价值。`verdict_record` 在代码层强制：判错却没填 `evidence` 会被当场拒绝。

**E9 需三重信号至少两项命中**（依据充分性 / 扰动检验 / 步骤删除检验）。把正确解答判成「蒙对」的代价很高，所以证据阈值高于其他类型。

### 4.3 稳定性：两次独立重评的真实方差

首轮曾用「同一条 verdict 原样重提 5 次」来做稳定性，得到 `step_mode_ratio = 1.0`。那个 1.0 只证明了「同一份 JSON 存五遍还是它自己」。已在代码层修掉：`stability()` 比对完整内容指纹，逐字相同即判机械重复，指标置空 —— **宁可没有指标，不要假满分**。

本轮改为**两趟完全独立的盲评**（第二趟在全新上下文中重新走完整流程，看不到第一趟任何判断），`n_identical_resubmissions = 0`：

| 一致性口径 | 两趟一致率 |
|---|---|
| process_valid（是否有误） | 0.933 |
| answer_correct | 0.900 |
| **完整 verdict（含步号与类型）** | **0.667** |
| 双方都判有误时的步号精确一致 | 0.68 |
| 双方都判有误时的 ±1 一致 | 0.90 |
| 错误类型一致 | 0.71 |

**「是否有误」很稳（0.93），「错在哪一步、属什么类型」不稳（0.67）。** 这是伪稳定性完全掩盖过的真实弱点，也解释了为什么精确定位只有 0.611 —— 评估器自己在这个判断上就存在方差。

### 5.1 四条「标注有问题」的具体证据（均经人工确认）

这是本轮最值得写的发现 —— **ProcessBench 的人工标注并非无误**，我们的指标因此是偏保守的。

以下四条预审意见**全部被人工确认**，其中 892、691 两条人工另做了独立复算。

**① gsm8k-307：标注错误（高置信）**
解答完整正确：50 + 50/2 = 75，75 − 30 = 45，答案 45 即 GSM8K 标准答案。但标注为 `process_correct: false, first_error_step: 2`。已独立复算，第 2 步无任何错误。评估器判「过程无误」是对的。

**② olympiadbench-892：标注漏标一个教科书级 E9（高置信）**
题目求 $T^2+(2T)^2+\cdots+(T^2)^2$ 的个位数，$T=49$。

- 项数 49 正确（末项 $(T^2)^2=(T\cdot T)^2$，故 $k$ 取 1..49）
- 但第 3 步称末位数字「每 9 项一循环」是**实质错误**：$(49k)^2 \bmod 10$ 的真实周期为 **10**，序列为 `[1,4,9,6,5,6,9,4,1,0]`
- 真实末位之和 **225**，题解算得 **245**
- **两者恰好同末位 5** —— 最终答案才「对」

标注为「过程无误」，漏掉了这个错误。这是本项目最想抓的那类样本：答案正确、过程不成立、且正确性纯属数值巧合。

（评估器的证据里称正确答案为 1 —— 那是把项数误当作 $T^2=2401$ 所致，证据部分有误，但核心结论成立。）

**③ olympiadbench-691：标注定位偏晚（高置信）**
$b+c=-1$ 且 $-20\le b,c\le 20$ 的整数对，枚举核验为 **40** 个（$c$ 取 −20..19），第 6 步声称 41 个是边界少算。第 7 步又扣掉根本不存在的整数重叠 $b=c=-1/2$。两处错误恰好抵消，答案 81 才对。首错在第 6 步，评估器指向第 6 步正确，标注指向第 7 步偏晚。

**④ olympiadbench-249：标注定位偏早（中置信）**
已用 SymPy 核验第 9 步：两根为 $90\pm34\sqrt7$，$34\sqrt7=2\sqrt{2023}$，两根之积为 8，故分母 $\sqrt[3]{90^2-(2\sqrt{2023})^2}=\sqrt[3]{8}=2$，通分结构正确 —— **第 9 步没有错**。真错在第 11 步：$(2\sqrt{2023})^2 = 4\times2023 = 8092$，题解写成 $8\times2023=16184$。评估器定位正确。

### 5.4 两类「双方都没错」的分歧，与由此确定的判定口径

两条分歧最终判为 `criterion_gap` —— 评估器与标注各按各的标准，都不算错。

**① olympiadbench-851：论证不完整**
题目要求「determine **all** functions」。第 8 步自述「plausible that this linear function
**might be** the only solution」，第 9 步即断言「**Hence**, the solution is $f(n)=n$」——
由「可能」跳到「就是」，唯一性未证。评估器判其过程不成立；ProcessBench 标注的是
「步骤内是否存在错误」，不标注「论证是否完整」。

**② math-912：表述含混但计算正确**
第 3 步称「绳子不完全直，需在两段之外再加上下垂量」，措辞确实误导；但随后按两段直线
计算 $\sqrt{5^2+12^2}+\sqrt{9^2+12^2}=13+15=28$ 是标准模型且结果正确。
（预审判为评估器漏报，**人工推翻**：措辞问题未影响任何一步的数值或结论。）

**据此确定的项目口径**（人工决定，已写入 `configs/taxonomy.yaml` 与 `docs/method.md`）：

> **不将「未证唯一性 / 论证不完整 / 表述含混」计入过程错误。本项目只标注步骤内的实质错误
> —— 即某一步的计算、代数变形、定理适用条件或概念使用本身不成立。**

这个口径必须明说，因为它直接决定误报率的分母：按此口径，两条从统计中**剔除**，
而不是计入误报或漏报。选择它的理由有二 ——

1. **可比性**：ProcessBench 的标注就是按这个口径做的。换口径会让本项目的指标无法与
   该数据集上的其他工作对照。
2. **可判定性**：「论证是否完整」缺少客观界线（严格到什么程度算证完？），把它纳入会
   引入大量不可复现的判断，与本项目「尽量把判定确定化」的主张相悖。

**代价要写明**：本项目因此**不覆盖**「每一步都对、但整体论证有缺口」这一类问题。
这是能力边界，不是已解决的问题。

## 6. 模型失败模式与能力边界

### 评估器侧

| 弱点 | 证据 | 归因 |
|---|---|---|
| **精确定位弱**（0.611） | 错多偏 1 步；两趟独立重评步号一致率仅 0.68 | 「首个」错误的界定本身有歧义：下游步骤沿用上游错误结论时，判首错在哪一步依赖对「错误传播起点」的理解 |
| **E9 召回低**（0.533） | 15 条 E9 只检出 8 条；两趟在 5+ 条上互相矛盾 | E9 要求识别「答案对但推导站不住」，是最需要全局把握的判断，且三重信号阈值刻意设高，牺牲召回换精度 |
| **T3 误报偏高**（0.500，n=4） | 2 条误报都在 T3 | 其中 1 条经核验实为标注漏标（892），另 1 条是准则差异（851）—— 修正后 T3 真误报为 0 |
| **L1 覆盖低**（触发 6.3%） | 87.5% 步骤返回 UNKNOWN | 自然语言步骤无法抽取可判定等式，属方法固有边界 |

### L1 确实赚到了

`check_step_symbolic` 在 omnimath-7 第 1 步抓到 $1+2+\cdots+666 = 1998$（真值 1563）。WorkBuddy 的评估流程起初把该样本判为「过程无误」，看到 L1 的 FALSE 后改判 E9。

**模型会放过的算术错误，SymPy 不会** —— 这是整个级联设计的立论，也是本轮唯一一次能明确归因到 L1 的贡献。

## 7. 工程实践中的两个教训

这两条不是指标，但比指标更值得记录。

### 7.1 确定性方法不是免费的可靠性

L1 初版在真实数据上的误报率是 **33.3%**（12/36），远超 ≤20% 门槛 —— 直接动摇了「把能确定判定的事从 LLM 手里拿走」这个立论。

逐条排查 12 条误报后发现：**没有一条是真正的判断分歧，全部是解析失败。** 根因是规范化器过于宽容 —— 遇到不认识的 LaTeX 命令就剥掉继续解析，解析出垃圾却「成功」了：

| 原文 | 剥掉后 | 判定 | 实际 |
|---|---|---|---|
| `\varphi(41) = 41 - 1` | `(41) = 40` | FALSE | φ(41)=40 ✓ |
| `\binom{40}{17} = \binom{40}{23}` | `(40)(17) = (40)(23)` | FALSE | 组合数相等 ✓ |
| `f(2) = 8 + 6 = 14 \tag{7}` | `14 * 7` | FALSE | ✓ |
| `\[71+72=143\] \[143+73=216\]` | 跨块拼成假等式 | FALSE | ✓ |

分四步修复至 3.6%：命令白名单（33.3%→12.5%）、公式块先切分、带余除法与函数下标豁免（→6.7%）、整除取整惯用法豁免（→3.6%）。10 条误报已全部固化为回归测试。

**教训**：确定性方法同样会因实现缺陷而系统性出错，而且因为它看起来「确定」，这类错误反而更不容易被怀疑。

### 7.2 用夹具测隔离逻辑，用真实数据测契约

loader 曾把 ProcessBench 的 `raw_label`（0-based 首错步号）塞进 `meta`，而 `without_label()` 只清 `label` 不清 `meta` —— **ground truth 随批次发给了模型**。

单元测试没抓到：夹具的 `meta` 是空的，**测试全绿而真实数据在泄漏**。是 WorkBuddy 端的评估流程主动声明「返回了 `meta.raw_label`，我全程忽略」才保住了那轮盲评。

修复：`SAFE_META_KEYS` 白名单（新增字段默认不外发）+ 专项测试 `test_no_label_leak.py`，**对真实样本集全量校验**。

**教训**：这类 bug 静默作废整轮验证 —— 不报错、不崩溃、指标照样算得出来，只是全都不可信。

## 8. 已知局限

1. **样本量小**。完整评估器只跑了 60 条（占抽样集 13%），各项指标 CI 较宽，误报率 CI 上界越线。分层结论（尤其 T3 的 n=4）不足以支撑精细比较。
2. **同源偏置**。以 Hy3 评判其他模型生成的推理链（ProcessBench 解答来自多个模型），缓解但未消除模型对自身错误类型不敏感的问题。
3. **人工抽检只覆盖了「分歧样本」**。16 条分歧已全部人工确认（§5），但一致的 44 条未逐条复核 —— 双方一致也可能同时错。这是抽检口径本身的局限。
4. **误报率 0.000 的 CI 上界仍有 0.143**。23 条无误样本不足以支撑「几乎不误报」的说法，只能说「大概率低于 15%」。
5. **判定口径排除了「论证不完整」**（§5.4）。此类问题本项目不覆盖，是明确的能力边界。
6. **E9 标注本身可能不完整**。892 一例已证明 ProcessBench 会漏标 E9，故实测 E9 召回（修正后 0.643）的分母也可能偏小。
7. **步骤切分粒度**与标注可能不完全对齐，故以 ±1 容忍为主要定位口径。
8. **Hy3 正式评测与 Max Mode 消融未做**（P6）。目前所有结论都是关于**评估器**的，尚未产出关于 Hy3 解题能力的结论。
